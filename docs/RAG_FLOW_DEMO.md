# RAG 流转演示（观测后台 · 第二期）

灵感来自 "TL;DR Crawler"：一只蜘蛛在网页上爬、边爬边挑关键句。它用蜘蛛是因为爬虫叫 crawler。
RAG 里负责找资料的组件在 LangChain 里叫 **Retriever**，字面就是"寻回犬"。所以本演示的主角是一只金毛寻回犬「小金」。

## 1. 三个问题

| 问题 | 回答 |
| --- | --- |
| 给谁用 | 讲课 / 演示时的听众：不懂技术的产品经理、学生 |
| 目标 | 30 秒看懂两件事：资料是怎么被"存进去"的；问题是怎么"找到答案"的 |
| 怎么用 | 后台「RAG 演示」页：一键导入演示资料 → 点预设问题 → 自动回放；也可以逐步点"下一步"边讲边停 |

不做：实时跟随鼠标、可编辑参数、多问题对比。只回放真实发生过的一次调用，保证"演示的就是系统真实做的"。

## 2. 世界观（贯穿两条流）

| RAG 概念 | 演示里的样子 | 一句话讲解 |
| --- | --- | --- |
| 资料原文 | 一张长纸条 | 你上传的文档 |
| 切分 chunk | 剪刀把纸条剪成卡片，相邻卡片有一截斜纹重叠 | 太长塞不进模型，切成 800 字左右的卡片；重叠 120 字防止一句话被剪断 |
| 向量 embedding | 卡片飞到「气味地图」上变成一个点 | 每张卡片被翻译成 1536 个数字，意思相近的卡片落得近。这里压成 2 维给你看 |
| 关键词 BM25 | 卡片挂上几个词签 | 同时记下卡片里有哪些词，供"按字面找" |
| 问题向量 | 问题也落到地图上，是小金闻到的"味道" | 问题用同一种翻译法变成数字 |
| 向量检索 | 小金沿地图跑向离味道最近的点（蓝线） | 按意思找 |
| 关键词检索 | 带同样词签的卡片亮起（橙色） | 按字面找 |
| RRF 融合 | 两份名单合并，两边都找到的卡片变金色 | 两种找法互补，合并取前 8 |
| 交给模型 | 小金把 8 张卡片叼到书桌，编号 [1]–[8] | 模型只看这 8 张卡片回答 |
| 引用校验 | 答案里的 [n] 连回卡片；越界编号被划掉 | 每句话都能追到原文；编造的编号会被删掉 |
| 全文模式 | 小金趴下不动："资料很少，全部直接给模型" | 资料少于 4 万字时不需要找 |

## 3. 演示案例：喵记咖啡

一套虚构的咖啡店资料（`examples/rag-demo/`），6 份文档约 3800 字。演示资料单独按 300 字切分（重叠 60 字），得到约 17 张卡片：
平时的 800 字切法只能切出 9 张左右，"取前 8 张"等于全选，看不出挑选；300 字的卡片也能在屏幕上读完。
资料里故意埋了能制造对比的内容，每个预设问题演示一个知识点。预设问题每次先清空演示笔记本的对话，互不影响；
自己输入的问题保留上文，可以用"那黑卡呢？"演示改写。

| 预设问题 | 讲什么 | 设计 |
| --- | --- | --- |
| 咖啡买错了还能把钱要回来吗？ | 按意思找赢了 | 资料写的是"订单取消与退款"，问题里没有"退款"二字；关键词只能命中满地的"咖啡"，向量找对了 |
| Q7303 是什么？ | 编号要靠字面 | 编号没有"意思"，向量只认出"像在说新品"，三张新品卡片分数挤在一起；关键词精确命中写着 Q7303 的卡片 |
| 金卡会员每个月送几杯？ | 两路都找到 | 两份名单都排在前面，合并后稳居第一 |
| 你们支持比特币支付吗？ | 资料里没有 | 所有点都离得远，模型应回答"资料未提及"，不编造 |

## 4. 两条流的分镜

### 资料怎么流转（回放一次导入）

1. 读取：纸条出现，显示字数
2. 切分：剪刀从上到下剪，卡片依次落下，重叠部分斜纹标出
3. 向量化：卡片飞到地图变成点，同一份资料同色
4. 贴词签：每张卡片挂 3–5 个关键词
5. 入库：显示 "N 张卡片 · 1536 维 · 耗时 / token"

### 问题怎么流转（回放一次问答）

1. 提问：问题气泡
2. 判断模式：资料总字数 vs 4 万字门槛；全文模式时小金趴下，直接跳到第 7 步
3. 改写：有上下文时，展示"那狗呢？"→"狗喜欢吃什么？"
4. 闻味道：问题落到地图上（星形），同时拆出关键词
5. 两路寻找：小金跑向向量前几名（蓝线 + 相似度）；关键词命中卡片亮橙色
6. 合并：两列名单 → 合并前 8，金色标出双命中
7. 叼回：8 张卡片编号排到书桌
8. 写答案：答案逐字出现，引用角标连回卡片；越界编号划掉

右侧讲解面板借鉴 TL;DR：步骤计数 "5 / 8"、进度条、每步一句大白话讲解 + 真实数据（分数、耗时、token）。

## 5. 数据与接口

演示只读「回放快照」，与 span 分开存，避免详情页 JSON 被大字段淹没：

```sql
CREATE TABLE flow_snapshots (run_id TEXT PRIMARY KEY, kind TEXT, data_json TEXT, created_at TEXT);
```

- 导入：`save` 节点写入 chunks（全文、序号、关键词）、2 维坐标、向量维度、切分参数
- 问答：`choose_mode` 写模式与字数；`retrieve` 写问题坐标、候选卡片坐标、两路完整排名、融合明细；`finalize` 写上下文顺序、原始答案中的引用编号与被丢弃编号
- 2 维坐标：检索时用 PCA 把候选卡片和问题向量一起投影，存下坐标，回放稳定；候选上限 400 张
- 旧记录没有快照：页面提示"这次调用发生在演示功能上线前，请重新提问"

接口：

- `GET /api/admin/flows?kind=ingest|chat` 有快照的调用列表
- `GET /api/admin/flows/{run_id}` 快照 + run 摘要 + 各节点耗时
- `POST /api/admin/demo/setup` 创建/复用「RAG 演示 · 喵记咖啡」笔记本并导入资料
- `ChatIn.force_rag`：强制检索开关，演示页默认打开

## 6. 已知取舍

- 2 维地图会失真：离得近不一定最相似。画面以连线和分数为准，讲解里明确说出来
- 按意思找会给每张卡片打分（前 20 名几乎覆盖全部卡片），所以画面只连前 5 名；金色 = 两路都排进前 5
- 导入回放把同一笔记本已有的卡片作为灰点一起投影，单份资料只有两三张卡片时地图也有参照
- 问答回放额外存一份原始答案，用于把越界引用编号原地划掉
- 动画用 SVG + requestAnimationFrame，不引新依赖；`prefers-reduced-motion` 时只做淡入
